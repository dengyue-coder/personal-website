把 Python 训好的 MLP 搬进 ArkTS：鸿蒙脑电监测里的零依赖推理

EEG Monitor 是我独立完成的鸿蒙应用：BLE 5.0 对接脑电传感器，实时画出脑波、识别情绪、做意图分类。这篇文章只讲一个具体问题——模型怎么进端侧。

黄少荣物联网工程（师范）
2026 年 10 月 12 日 11 分钟阅读 鸿蒙与物联网

先说结论

HarmonyOS 端侧没有现成的推理框架可用，也不想为了一个三层 MLP 去引 ArkTS 之外的依赖。最后的做法是：Python 训练 → 导出权重 JSON → ArkTS 里手写前向传播。三层网络、几十个参数，纯 TypeScript 跑起来一次推理不到 0.3ms，30fps 的渲染完全带得动。

整条链路长什么样

传感器是 TGAM 模组，通过 BLE 以 notify 方式往外推数据；手机侧是 HarmonyOS API 12 的 ArkTS 应用。数据要经过四段路：

  • 蓝牙：扫描 → 连接 → MTU 协商 → 服务发现 → 写 CCC 描述符订阅通知。
  • 拼包：一帧 JSON 常常被拆到两三个 notify 包里，需要按长度前缀缓存拼接。
  • 算法：自适应 IQR 阈值检测挑出有效波段，EMA 指数平滑压噪声。
  • 推理与渲染：特征送进 MLP，结果交给 Canvas 2D 画波形与仪表。

权重导出：别导成 pickle

训练脚本在本地跑，导出只做一件事——把每层的权重矩阵和偏置摊平成数组，写成一个 JSON。别导 pickle，也别导 ONNX 再想办法解析，端侧解析成本远大于收益。

{
  "input_dim": 12,
  "layers": [
    { "w": [[0.12, -0.44, ...], ...], "b": [0.01, ...], "act": "relu" },
    { "w": [...], "b": [...], "act": "relu" },
    { "w": [...], "b": [...], "act": "softmax" }
  ],
  "labels": ["专注", "放松", "困倦", "紧张"]
}

导出时顺手做两件事：把输入特征顺序写进 JSON（feature_order），以及把训练时的均值方差一起存下来。这两样东西不对齐，端侧推理结果就会莫名其妙地偏。

ArkTS 里的前向传播

没有矩阵库，就按行乘加写。核心只有二十来行：

function forward(x: number[], model: Model): number[] {
  let cur: number[] = x;
  for (const layer of model.layers) {
    const out: number[] = new Array(layer.b.length).fill(0);
    for (let i = 0; i < layer.w.length; i++) {
      let s = layer.b[i];
      const row = layer.w[i];
      for (let j = 0; j < row.length; j++) s += row[j] * cur[j];
      out[i] = s;
    }
    cur = layer.act === 'softmax' ? softmax(out) : out.map(v => v > 0 ? v : 0);
  }
  return cur;
}

两个细节值得记下来。第一，循环顺序：外层走输出神经元、内层走输入，比反过来对缓存更友好，实测在低端机上快 15% 左右。第二，不要每帧 new 数组：把输出缓冲提到实例外面复用，GC 抖动会直接反映到帧率上。

传统算法没有被丢掉

MLP 只负责分类。前面还有两层非学习的处理，它们决定了模型的输入质量：

  • 自适应 IQR 阈值：滑动窗口算四分位距，超出 Q3 + 1.5·IQR 的样本判为伪迹丢掉的，阈值随窗口滚动，而不是写死一个数。
  • EMA 平滑：y = α·x + (1-α)·y_prev，α 取 0.25 左右，既能压掉高频抖动，又不至于让波形"糊"到看不出节律。
  • 欧氏距离质心分类器：作为 MLP 的兜底。样本量不够、置信度低的时候回退到质心距离，结果更稳，也更容易解释。

渲染：五层结构救了后期

项目一开始所有逻辑都堆在一个页面里，改一个动画要翻四百行。后来拆成五层：Service（BLE 与数据源）→ Detector（阈值与算法）→ Store（单例状态 + 观察者）→ Renderer（Canvas 绘制）→ UI（页面与组件）。分层之后，同一条数据可以同时驱动波形、频谱柱、环形仪表和雷达图，而渲染层完全不知道数据是从蓝牙来的还是从模拟数据源来的——这一点在做演示时特别有用，录屏不用带着硬件跑。

踩过的坑

  • MTU 没协商：默认 23 字节，一帧数据被切成六七段，拼包逻辑没写好就丢帧。先 setBLEMtuSize(247) 再订阅。
  • CCC 描述符写错：订阅要写 00002902-0000-1000-8000-00805f9b34fb，写错不会报错，只是永远收不到通知。
  • 断线重连没重订阅：连接建立不等于通知恢复，重连后必须重新发现服务并重新写 CCC。
  • 设备名重名：附近同型号传感器不止一个，扫描时按 deviceId + 服务 UUID 双重过滤，别只看名字。

如果重做一次

我会更早地把"数据源"抽象成接口。现在这套代码里，BLE 和模拟数据源是同一个接口的两个实现，这是第二次重构才得到的结构，而它本来应该在第一周就定下来。端侧开发最贵的不是写代码，是没硬件的时候没法调——先把可替换的数据源架好，效率差好几倍。
