银铃陪护小程序测试复盘：那些“看起来没问题”的缺陷

银铃陪护是面向老年群体的三端志愿服务小程序（学生端、长者端、管理端）。我负责需求分析与测试设计。这篇复盘我找到的那几类缺陷，以及怎么让它们被找到。

2026 年 5 月 16 日 8 分钟阅读 软件测试

先画流程，再写用例

三端意味着三条流程，且互相咬合：长者发起陪伴预约 → 学生接单 → 服务完成 → 双方评价 → 数据回流看板。上来就写用例，很容易只覆盖单端而漏掉流转。

所以第一步是把三端流程画成一张图，标出每次跨端的数据交接点。这些交接点就是最容易出问题的地方，也是用例的优先级来源。

用例设计：三种方法用在三种地方

  • 等价类 + 边界值：预约时间、服务时长、人数上限这类数值输入。特别注意"跨天""刚好等于上限""上限 -1"。
  • 场景法：主流程 + 异常分支。比如接单后学生取消、服务中超时、评价提交时网络中断。
  • 因果图：服务匹配规则——时间匹配、类型匹配、专业匹配三个条件组合，共八种情况，逐一验证匹配结果是否符合预期优先级。

服务匹配是最容易出隐性 bug 的模块：三个条件都满足时排在最前，只满足两个时怎么排？如果产品没定义清楚，测试就该把它提成问题，而不是自己猜一个预期。

三类"看起来没问题"的缺陷

1. 看板数据异常

管理端首页的"累计服务人次"和"本周新增"对不上，差值恒等于某个固定数。查下来是统计 SQL 的 where 条件里时间范围用了 between 但漏了时分秒，把上周末的数据算进了本周。这类问题在测试环境数据量小时几乎看不出来，必须构造跨周期数据。

2. 系统名称不一致

同一个产品在登录页、页脚、消息推送模板里出现了三种叫法。这不是功能缺陷，但属于品牌一致性问题，用户会直接怀疑"这是不是山寨的"。处理方式：整理一份文案基线表，逐处比对；后续把它写进提测清单。

3. 测试数据混进真实列表

列表里出现了"测试测试""张三111"这类记录，且能在管理端被编辑。根因是初始化脚本直接跑在了预发布库。除了清数据，更重要的是加约束：初始化脚本只在空库执行，并对明显测试用词做校验拦截。

一条能复现的缺陷单长什么样

【标题】管理端首页“本周新增服务”统计包含上周日数据
【环境】预发布 / 管理端 / Chrome 120
【前置】存在 3 条 2026-05-11（上周日）完成的服务记录
【步骤】1. 登录管理端 2. 进入首页看板 3. 对比“本周新增”与按周筛选的列表条数
【预期】本周新增 = 本周一至今天完成的记录数 = 5
【实际】显示 8，多出上周日 3 条
【定位建议】统计 SQL 的时间范围边界可能未含时分秒
【严重程度】中 / 优先级 高

关键在【前置】和【定位建议】：让开发能一次复现，而不是来回问三轮。

三端一致性怎么验

界面点一遍只能证明"看起来对"，数据一致性要靠对账：

  • 每条预约在三个端的列表里都应存在，且状态机流转一致；
  • 用 SQL 统计各状态数量，与三端页面显示的计数逐项核对；
  • 评价数据必须能反查到对应服务记录，不能出现"孤儿评价"。

对账 SQL 我一般写成一段可重复执行的脚本，每轮回归跑一次，比人工数数可靠。

复盘

这次项目让我确认了一件事：测试的价值不在于发现崩溃，而在于发现"用户一定会注意到、开发一定没注意到"的细节。为此，用例之外还需要两类输入——一份文案基线表，一套可重复的对账脚本。这两样东西在这个项目之后成了我的标配。
